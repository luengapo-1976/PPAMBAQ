# LOGICA DE NEGOCIO

Directrices para la distribución de la lógica de negocio

Toda la lógica de negocio deberá implementarse en NestJS. La base de datos PostgreSQL (Supabase) tendrá como responsabilidad principal el almacenamiento y la integridad de la información, evitando trasladar reglas de negocio complejas al motor de base de datos.

En PostgreSQL únicamente se implementarán funciones, procedimientos o triggers cuando aporten un beneficio claro en términos de rendimiento, integridad o automatización de procesos propios de la base de datos.

En particular:

NestJS será responsable de:
Validaciones de negocio.
Flujos de aprobación.
Reglas para cambios de estado.
Autenticación y autorización.
Gestión de roles y permisos.
Procesamiento de solicitudes.
Integración con servicios externos.
Envío de notificaciones.
Generación de reportes y consultas de negocio.
Orquestación de transacciones entre múltiples entidades.
PostgreSQL será responsable de:
Almacenamiento persistente de la información.
Integridad referencial mediante claves foráneas.
Restricciones (CHECK, UNIQUE, NOT NULL).
Índices para optimizar consultas.
Vistas para simplificar consultas complejas.
Funciones SQL únicamente cuando mejoren significativamente el rendimiento o reutilicen lógica de acceso a datos.
Triggers exclusivamente para auditoría, actualización automática de campos (por ejemplo updated_at) o mantenimiento de información técnica.
No se deberán implementar en la base de datos:
Procesos de aprobación.
Validaciones funcionales.
Reglas de negocio.
Cálculos propios del dominio.
Flujo de estados.
Lógica dependiente del perfil del usuario.
Procesos que puedan implementarse de forma más clara y mantenible en NestJS.


# FRONT END

La aplicación deberá desarrollarse con una arquitectura moderna de tres capas. El frontend se implementará en Angular, siguiendo una arquitectura modular, componentes reutilizables, diseño responsive y comunicación exclusiva mediante APIs REST. El backend se desarrollará en NestJS con TypeScript, aplicando una arquitectura por módulos, separando claramente controladores, servicios y repositorios, e implementando autenticación basada en JWT, autorización por roles y validaciones de negocio. Como plataforma de datos se utilizará Supabase, aprovechando PostgreSQL como base de datos principal, Supabase Auth para la autenticación de usuarios, Storage para almacenar documentos o archivos adjuntos si son necesarios, y las políticas de Row Level Security (RLS) para reforzar la seguridad de acceso a los datos. La aplicación deberá diseñarse para operar 24x7, ser escalable, segura y fácilmente mantenible, utilizando variables de entorno para la configuración, migraciones para el control de cambios del esquema de la base de datos, auditoría de operaciones críticas, manejo centralizado de errores y registro de eventos (logging). La comunicación entre Angular, NestJS y Supabase deberá realizarse siempre mediante conexiones seguras (HTTPS), siguiendo buenas prácticas de desarrollo, seguridad y rendimiento.

# DESPLIEGUE / "REFRESH" DEL REPOSITORIO EN GITHUB

Cuando se pida "refrescar" o "subir los cambios al repositorio de GitHub", tener en cuenta que esto tiene DOS partes independientes, y hay que confirmar con el usuario cuál(es) aplica(n):

1. **Código fuente** → rama `main` (push normal con git). Esto NO actualiza el sitio en producción.
2. **Sitio en producción (GitHub Pages)** → rama `gh-pages`, servida en `https://luengapo-1976.github.io/PPAMBAQ/`. Es un build compilado aparte, publicado con `angular-cli-ghpages`. Solo se actualiza si se reconstruye y se vuelve a publicar explícitamente:

   ```
   cd frontend
   MSYS_NO_PATHCONV=1 npx ng build --configuration production --base-href /PPAMBAQ/
   npx angular-cli-ghpages --dir=dist/frontend/browser --branch=gh-pages
   ```

   - El `base-href` DEBE quedar `/PPAMBAQ/` (repo project page, sin dominio custom). Verificar siempre después del build con `grep '<base href' dist/frontend/browser/index.html` antes de publicar.
   - **Gotcha de Git Bash en Windows**: cualquier argumento que empiece con `/` (como `/PPAMBAQ/`) puede ser reinterpretado por MSYS como una ruta de archivo de Windows (ej. termina siendo `C:/Program Files/Git/PPAMBAQ/`), lo que rompe el `base href` y deja la app completamente en blanco (ni el login carga). Por eso el build SIEMPRE debe correr con `MSYS_NO_PATHCONV=1` delante cuando se use `--base-href` en Git Bash.
   - Backend de producción: `https://ppambaq.onrender.com` (Render). Su CORS solo permite el origin `https://luengapo-1976.github.io`, así que pruebas locales contra ese backend (`localhost`) fallarán por CORS — es esperado, no es un bug real.
   - Después de publicar, GitHub Pages puede tardar ~1 minuto en refrescar el CDN. Verificar con `curl` (con un query param cache-buster) o Playwright antes de concluir que el deploy no sirvió.

Si el usuario solo dice "sube/refresca el repo" sin más contexto, y hay cambios de frontend pendientes, preguntar explícitamente si además de subir el código a `main` quiere republicar el sitio en `gh-pages` — son pasos distintos y asumir solo uno puede dejar al usuario probando una versión vieja del sitio.
